## Executive Summary

| 항목 | 내용 |
|---|---|
| 기능 | 연차관리(유급/무급 구분) + 공통 결재 엔진 + 캘린더(휴가 연동) + **출퇴근 체크(근태)** + 일일/주간 업무보고(자동 초안) |
| 선택 설계안 | Option C — ApprovalLine + Approval 2개 핵심 테이블 기반 결재 엔진 |
| 핵심 데이터 모델 | CompanySettings, Department, User, LeavePolicy/LeaveTypeConfig(카테고리·급여유형)/LeaveBalance/LeaveRequest/Attachment, ApprovalLine/ApprovalLineStep/Approval/ApprovalStepLog, Event, **AttendanceRecord**, DailyReport, WeeklyReport, Notification |
| 핵심 로직 | 연차 이중 산정(회계연도/입사일), 연차차감형/특별휴가/공가 3카테고리 구분과 증빙·유급무급 검증, 결재선 스냅샷 기반 다단계 결재, 캘린더 병합 조회(Event+LeaveRequest)와 업무보고 휴가 연계 배지, **18:00 이후만 허용되는 퇴근 체크와 근태-휴가 병합 조회**, 일보→주보 자동 초안 승계 |
| 구현 모듈 | 8개 모듈(회사·조직·인증·관리자 → 결재엔진 → 연차 → 캘린더 → **근태** → 일보 → 주보 → 대시보드/알림) |

**Value Delivered**

| 관점 | 내용 |
|---|---|
| Problem | 문서 종류(연차/일보/주보)마다 결재 로직을 따로 만들면 유지보수 비용이 커지고, 부서별로 다른 결재선을 반영하기 어려움 |
| Solution | `ApprovalLine`(부서×문서유형 결재선 정의) + `Approval`(대상 문서를 참조하는 상신 건) 2개 테이블로 결재 엔진을 공통화 |
| Function/UX Effect | 문서 종류가 늘어나도 결재 화면·로직 재사용 가능, 관리자는 회사정보·조직·사용자·결재선·연차정책을 하나의 관리자 영역에서 관리, 연차 신청 시 카테고리별로 잔여연차 차감/증빙 첨부가 자동 분기 |
| Core Value | 결재 엔진 중복 제거로 구현 공수 절감 + 연차 차감 오류 방지 + 향후 문서 유형 확장(예: 지출결의 등) 시 재사용 가능한 구조 확보 |

## 1. Overview

본 설계서는 [Plan 문서](../../01-plan/업무관리플랫폼_개발계획서.md)에서 정의한 필수 기능(연차관리, 결재, 일일/주간 업무보고)을 어떤 데이터 구조·API·화면 흐름으로 구현할지 정의한다. 핵심 설계 결정은 **"결재 엔진을 3종 문서(연차/일보/주보)가 공유하는 독립 도메인으로 둔다"**는 것이며, 이로써 문서 종류가 늘어나도 결재 로직을 재사용할 수 있다.

## 2. 아키텍처 선택 근거 (Option C 채택)

| 옵션 | 요약 | 채택 여부 |
|---|---|---|
| A. 최소 변경 | 문서별 승인 필드 개별 관리 | ❌ 문서 종류 확장 시 구조 반복, 다단계 결재 표현 어려움 |
| B. 클린 아키텍처 | 완전 독립 워크플로우 엔진(무제한 단계, 병렬 결재 등) | ❌ 현재 요구사항(부서별 1~3단계) 대비 과설계, 구현 공수 과다 |
| **C. 실용적 균형 (채택)** | `ApprovalLine`(부서×문서유형, 1~3단계) + `Approval`(polymorphic 참조) 2개 핵심 테이블 | ✅ 요구사항을 정확히 충족하면서 구현 공수 최소화 |

|---|---|---|
| id | PK | |
| code | enum: ANNUAL_DAY \| ANNUAL_HOUR \| OFFICIAL \| CONGRATULATION \| SICK | 기존 HALF_AM/HALF_PM/QUARTER(오전·오후반차, 반반차)는 `ANNUAL_HOUR`로 통합되어 폐지 |

## 4. 핵심 로직 설계

### 4.1 연차 산정 로직 (회계연도 / 입사일 이중 기준)

- 부서(Department.leaveBasis)에 설정된 기준에 따라 사용자의 `LeaveBalance` 갱신 시점이 결정된다.
  - **회계연도 기준**: 매년 1월 1일, 전 직원 일괄 갱신 배치 실행. 해당 연도 중도 입사자는 입사일부터 12/31까지 잔여 개월 수 비례로 `LeavePolicy.grantDays`를 월할 계산.
  - **입사일 기준**: 사용자별 입사일(`User.hireDate`)의 매년 응당일에 개별 갱신 배치 실행. 근속연수는 입사일 기준으로 계산해 `LeavePolicy` 구간 매칭.
- 두 기준 모두 동일한 `LeavePolicy`(근속연수 구간 테이블)를 참조하되, "근속연수 계산 시작점"과 "갱신 시점"만 달라지는 구조로 설계해 로직 중복을 없앤다.
- `LeaveRequest` 상신 시 `inputMode`에 따라 차감일수(`days`)를 계산한다.
  - **DAY_RANGE**(연차(일), 특별휴가, 공가): 근무일수 계산(`businessDaysBetween`)
  - **HOUR_RANGE**(연차(시간)):
    1. `rawHours = endTime - startTime`
    2. 점심시간(`CompanySettings.lunchStart~lunchEnd`)과 겹치는 구간은 자동 제외 → `usedHours = rawHours - overlap`
    3. `usedHours`가 `hourlyLeaveUnitHours`의 배수가 아니거나 `hourlyLeaveMaxHours`를 초과하면 **상신 자체를 차단**(연차(일) 사용 안내)
    4. `days = usedHours / standardWorkHoursPerDay` (일 단위로 환산해 `LeaveBalance`에서 차감)
- `category=ANNUAL_DEDUCT`인 경우(연차(일)·연차(시간) 모두)에만 잔여연차(`LeaveBalance.granted - used`) 검증 후 상신 허용. `SPECIAL`/`OFFICIAL`은 잔여연차 검증 없이 상신하되, `requireAttachment=true`면 `Attachment` 첨부 여부를 검증한다.

### 4.2 결재 처리 흐름 (공통 엔진)

1. 문서(연차/일보/주보) 상신 시, `사용자의 소속 부서 + 문서유형`으로 활성 `ApprovalLine` 조회 → 해당 라인의 `ApprovalLineStep` 목록으로 `Approval` 레코드 생성(스냅샷), `currentStep=1`, `status=PENDING`.
2. 결재자는 자신이 `ApprovalLineStep.approverUserId`이거나, 해당 기간 `DelegateAssignment`의 대결자인 결재 건을 결재함에서 조회.
3. 승인 처리 시 `ApprovalStepLog` 기록 → 마지막 단계면 `Approval.status=APPROVED`(+대상 문서 status 동기화), 아니면 `currentStep+1`.
4. 반려 시 즉시 `Approval.status=REJECTED`, 대상 문서 status 동기화, `Notification` 발송.
5. 회수(RECALLED)는 `currentStep=1` && 이력 없음 상태에서만 신청자 본인이 실행 가능.

### 4.3 일일업무보고 자동 초안 로직

```
DailyReport 작성 화면 진입(reportDate = D)
  → 직전 영업일(D-1, 주말 제외) 기준으로
     WHERE userId = 현재사용자 AND reportDate = 직전영업일
     인 DailyReport 조회
  → 존재하면: todayResult 초안 = 해당 레코드의 tomorrowPlan
  → 없으면(최초 작성/미작성): todayResult 초안 = "" (빈 값)
  → 사용자는 초안을 확인 후 자유 수정 가능
  → tomorrowPlan, notes는 신규 입력
```

### 4.4 주간업무보고 자동 취합 로직

```
WeeklyReport 작성 화면 진입(weekStart, weekEnd)
  → WHERE userId = 현재사용자 AND reportDate BETWEEN weekStart AND weekEnd
     인 DailyReport 목록을 날짜순으로 조회
  → thisWeekResult 초안 = 조회된 각 DailyReport.todayResult를
     날짜 라벨과 함께 순서대로 이어붙인 텍스트
     예) "[08/11] ... \n[08/12] ... \n[08/13] ..."
  → 해당 주간에 작성되지 않은 날짜는 자동으로 목록에서 제외
  → 사용자는 취합된 초안을 요약/정리하여 수정 가능
  → nextWeekPlan, notes는 신규 입력
```

> 리스크(Plan 8장)로 식별된 "주중에 미리 작성 시 처리"는, 작성 시점까지 존재하는 DailyReport만 취합하고 이후 재열람 시 재취합(덮어쓰기 여부는 사용자 확인 후)하는 방식으로 처리한다. 상신 완료된 WeeklyReport는 재취합 대상에서 제외(고정).

### 4.5 캘린더 병합 조회 및 업무보고 연계

```
캘린더 화면 진입(month = YYYY-MM)
  → Event WHERE startAt가 해당 월에 포함 (departmentTag 필터 선택 시 department 일치 또는 null)
  → LeaveRequest WHERE status='APPROVED' AND 기간이 해당 월과 겹침
  → 두 결과를 날짜별로 병합해 월간 뷰에 표시(휴가는 신청자 이름 태그, 일정은 제목 태그)
```

- 일일업무보고 작성 화면 진입 시, 전일(직전 영업일)에 **본인**의 승인된 `LeaveRequest`가 있으면 "전일은 휴가였습니다" 배지를 노출(자동 초안이 비어 있는 이유를 알려줌).
- 주간업무보고 작성 화면 진입 시, 해당 주간에 **본인 또는 같은 부서 팀원**의 승인된 `LeaveRequest`가 있으면 인원수·일자 배지를 노출.
- 캘린더 데이터는 신규 테이블 없이 `Event` + 기존 `LeaveRequest`를 재사용하므로 별도 동기화 로직이 필요 없다(단일 진실 원천 유지).

### 4.6 출퇴근 체크 로직

```
[대시보드] 출근 체크: 당일 AttendanceRecord가 없으면 생성(checkInAt=현재시각). 이미 있으면 버튼 비활성("이미 출근 체크됨").
[대시보드] 퇴근 체크: 서버 기준 현재 시각에 따라 3단계로 판단한다.
          - 18:00 이전: 버튼 비활성 + 안내("18:00 이후 가능합니다")
          - 18:00~19:00: 출근 기록이 있으면 누구나 체크 가능
          - 19:00 이후: 당일 승인된 OvertimeRequest가 있는 경우에만 체크 가능(없으면 "19:00 이후는 초과근무 승인 필요" 안내)
[배치/자동 처리] 퇴근 미체크 + 18:30 경과 + 당일 승인된 OvertimeRequest 없음 → checkOutAt을 18:00으로 자동 기록(레코드에 auto=true 플래그).
          당일 승인된 초과근무가 있으면 계속 근무 중으로 간주해 자동 마감하지 않는다.
[출퇴근 메뉴] 월별 근태 조회: 조회 년월(기본값 당월) 선택 → 대상 사용자(MEMBER/APPROVER는 본인 고정,
          ADMIN은 구성원 목록에서 선택)의 AttendanceRecord LEFT JOIN LeaveRequest(status=APPROVED, 기간 겹침)
          → 휴가가 있는 날은 status=LEAVE로 표시, LeaveTypeConfig.payType이 UNPAID면 "무급" 배지 함께 표시.
          → 월간 요약(출근일수/휴가일수/미체크일수) 집계 표시.
```

- 출퇴근 **체크 액션**은 대시보드에 배치하고, "출퇴근" 메뉴는 **조회 전용**(월별 근태 현황)으로 역할을 분리한다.
- 18:00 기준은 **서버(또는 클라이언트 신뢰 불가 시 서버) 시각**을 기준으로 판단해 클라이언트 시계 조작을 방지한다.
- 출근 없이 퇴근만 체크하는 경우는 허용하지 않는다(출근 기록 존재를 전제 조건으로 검증).
- ADMIN이 타인의 월별 근태를 조회할 때는 체크인/체크아웃 액션 없이 **읽기 전용**으로 제공한다.

### 4.7 대기중 신청 건 수정·취소 (동시성·무결성 보장)

**적용 대상**: `LeaveRequest`, `DailyReport`, `WeeklyReport`, `OvertimeRequest` — 공통 결재 엔진을 쓰는 4종 문서 모두 동일 정책을 적용한다.

**허용 조건**
```
수정/취소 가능 = 문서.status === 'PENDING'
              && Approval.currentStep === 1
              && 해당 Approval에 ApprovalStepLog가 1건도 없음
```
즉 **어느 결재자도 아직 처리하지 않은 상태**일 때만 신청자 본인이 수정·취소할 수 있다. 다단계 결재선에서 1차 승인자가 이미 승인해 2단계로 넘어간 경우는 (이미 검토한 결재자의 판단을 무효화하지 않기 위해) 수정·취소를 막는다 — 기존 `RECALLED` 규칙(§3.2)과 동일한 조건이며, "수정"은 이 조건에 "취소"를 더한 것으로 이해하면 된다.

**동시성 제어 — 신청자 측**: 대상 문서 테이블에 `version`(정수) 컬럼을 둔다. 수정·취소 API는 단일 원자적 쿼리로 처리한다.

```sql
UPDATE leave_requests
SET ..., version = version + 1
WHERE id = :id AND version = :clientVersion AND status = 'PENDING'
```

- 영향받은 row가 0건이면 **409 Conflict** — 클라이언트가 화면을 열었던 시점 이후 이미 다른 곳(결재자의 승인/반려, 또는 다른 세션의 수정)에서 상태가 바뀐 것이다. 최신 데이터를 다시 불러와 **"이미 처리되어 변경할 수 없습니다"** 안내 후 화면을 갱신한다.
- 성공 시 `version`이 1 증가하며, 이후의 결재 처리는 이 새 버전을 기준으로 검증된다.

**동시성 제어 — 결재자 측(요청하신 "승인 타이밍" 무결성의 핵심)**: 결재자가 상세보기를 연 시점의 문서 `version`을 승인/반려 요청에 함께 보낸다(`Approval.targetVersion`). 서버는 승인 처리 직전에도 대상 문서의 현재 `version`과 비교한다.

```
승인/반려 처리 시:
  if 문서.version !== 결재자가 들고 있던 version:
    → 그 사이 신청자가 내용을 수정했다는 뜻 → 승인 처리 거부
    → "신청 내용이 변경되었습니다. 새로고침 후 다시 확인해주세요" 반환
  else:
    → 정상 승인/반려 처리, Approval.status 갱신
```
이렇게 하면 결재자가 화면에 띄워둔 **오래된 내용을 보고 실수로 승인**하는 상황을 막을 수 있다 — 신청자의 수정과 결재자의 승인이 동시에 일어나도 어느 한쪽만 반영되고, 나머지는 명확한 안내와 함께 재시도를 유도한다(낙관적 잠금, Lost Update 방지).

**연차 잔여일수 처리**: `category=ANNUAL_DEDUCT`인 `LeaveRequest`는 **상신 시점에 `LeaveBalance.used`를 선반영(예약)**하는 구조이므로(§4.1), 취소 시 선반영분을 환원하고, 수정 시에는 기존 선반영분을 환원한 뒤 새 일수를 재검증(`잔여연차 >= 새 일수` 확인)하고 재반영한다. 검증 실패 시(수정한 일수가 잔여연차를 초과) 저장을 차단한다.

**UX 원칙**: 수정 폼은 새로 신청하는 폼과 동일한 화면을 재사용하되, 기존 값이 채워진 채로 열리고 제출 버튼 라벨만 "수정 저장"으로 바뀐다. 결재함 목록/상세에는 `editedAt`이 있는 건에 "수정됨" 배지를 표시해 결재자가 인지할 수 있게 한다.

| 인사정보 | `GET/PUT /hr-records/me` | 본인 인사기록카드 조회/저장 |
| 초과근무 | `POST /overtime-requests` | 신청(19:00 이후 예상 퇴근시간 검증 + Approval 생성) |
| 초과근무 | `GET /overtime-requests/me?date=` | 당일 승인 여부 확인(퇴근 체크 게이트에 사용) |
| 관리자 | `GET/PUT /company-settings` | 회사 기본정보 조회/수정(1건) |
| 관리자 | `CRUD /departments`, `/users`, `/approval-lines`, `/approval-line-steps`, `/leave-policies`, `/leave-type-configs` | 조직·사용자·정책 관리 |

## 6. 화면 흐름 (Plan 6장 화면 목록에 대응)

- 연차 신청 화면: 유형 선택(카테고리별 그룹 표시: 연차차감형/특별휴가/공가) → 기간 입력 → 연차차감형이면 잔여연차 실시간 표시, 특별휴가·공가면 잔여연차 표시 대신 증빙파일 첨부 영역 노출(`requireAttachment=true`면 필수 표시) → 상신
- 관리자 - 회사 기본정보: 회사명·사업자등록번호·대표자·근무제·전사 기본 연차산정기준 입력 폼(1건 수정)
- 관리자 - 사용자 관리: 사용자 목록/검색 → 부서·직급·역할 배정, 퇴사 처리
- 대시보드: "출근"/"퇴근" 체크 카드 배치 — 퇴근은 18:00 이전엔 비활성 + 안내 문구, 이후 활성. 체크 시 시각 기록
- 출퇴근 화면(조회 전용): 조회 년월(기본값 당월) 선택 → 본인 일자별 근태(휴가일은 유형+무급 배지 표시) + 월간 요약. **ADMIN은 진입 시 전 직원 요약 목록이 먼저 표시**되고, 행 클릭 시 해당 직원의 상세로 드릴다운(뒤로가기로 목록 복귀)
- 캘린더 화면: 월간 뷰 진입 시 `GET /calendar` 호출 → 승인된 휴가(이름 태그) + 사내 일정(제목 태그)이 날짜별로 병합 표시 → 부서 필터 선택 가능 → "일정 등록" 버튼으로 Event 생성(전 직원 가능, 본인 건만 수정·삭제)
- 일일업무보고 작성 화면: 진입 시 `GET /daily-reports/draft` 자동 호출 → 당일실적 필드에 초안 자동 채움(수정 가능 표시) → 전일 본인 휴가가 있었다면 안내 배지 표시 → 다음날계획/보고사항 입력 → 상신
- 주간업무보고 작성 화면: 진입 시 `GET /weekly-reports/draft` 자동 호출 → 금주실적 필드에 취합 초안 자동 채움(수정 가능 표시) → 해당 주간 팀원 휴가 인원·일자 배지 표시 → 차주계획/보고사항 입력 → 상신
- 통합 결재함: 문서유형 탭(연차/일보/주보) 또는 통합 목록, 승인/반려 처리
- 관리자 결재선 설정: 부서 선택 → 문서유형별 단계·승인자 지정(ApprovalLineStep) UI

## 7. 권한(RBAC) 설계

| 역할 | 접근 범위 |
|---|---|
| MEMBER | 본인 데이터 조회/작성/상신만 가능 |
| APPROVER | MEMBER 권한 + 본인이 승인자로 지정된 결재 건 처리, 팀원 데이터 조회(소속 부서 범위) |
| (전 역할 공통) | 캘린더 조회 및 사내 일정(Event) 등록 가능, 본인이 등록한 Event만 수정·삭제 |
| (전 역할 공통) | 본인 출퇴근 체크 및 본인 월별 근태 조회 가능. **타 직원 근태 조회는 ADMIN만 가능** |
| ADMIN | 회사 기본정보·전사 조직/사용자/결재선/연차정책(카테고리·증빙 필수 여부 포함) 관리, 전체 데이터 조회 |

## 8. 테스트 계획 (핵심 시나리오)

1. 연차: 회계연도 기준 중도입사자 비례 계산 / 입사일 기준 근속연수 구간 매칭
2. 연차: 반차·반반차 신청 시 잔여연차 정확히 차감
2-1. 연차: 특별휴가·공가(SPECIAL/OFFICIAL) 신청 시 잔여연차 차감 없이 처리되고, 증빙 미첨부 시 상신 차단
3. 결재: 2단계 결재선에서 1차 승인 후 2차로 정상 이관, 어느 단계든 반려 시 즉시 종료
4. 결재: 대결자가 지정 기간 내 정상 처리 가능
5. 일보: 전일 다음날계획이 당일실적 초안에 정확히 반영 / 전일 미작성 시 빈 값
6. 주보: 해당 주 일보들의 당일실적이 날짜순으로 취합되어 초안 표시, 미작성일 제외
7. 캘린더: 승인된 휴가와 사내 일정이 월간 뷰에 정확히 병합 표시, 부서 필터 정상 동작, 본인이 등록하지 않은 일정은 수정·삭제 버튼 비활성화
8. 업무보고 연계: 전일 본인 휴가 시 일보 화면에 안내 배지 표시 / 팀원 휴가가 있는 주간은 주보 화면에 인원 배지 표시
9. 근태: 18:00 이전 퇴근 체크 버튼 비활성 확인 / 18:00 이후 정상 기록 / 출근 기록 없이 퇴근 체크 불가 확인
10. 근태: 병가로 처리된 날짜가 근태기록에 "무급"으로 정확히 표시되는지 확인
